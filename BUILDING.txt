Super Monkey Ball Deluxe: native recompilation and bring-up

Windows prerequisites: LLVM 22.1+ (clang-cl, LLD), Ninja, Visual Studio 2026 C++
tools and Windows SDK, CMake 4.2+, Git, PowerShell and JDK 21+.
No Python is used. Controller-driven play through the first level is verified.

Windows release installer:

  .\tools\Package.ps1

This builds and packages the current release with one worker. Use -SkipBuild
to package already-built game and tool binaries. The installer is written to build/release with a SHA-256 checksum
and release.json. Only the Runtime component is packaged: game, diagnostics,
application-local C++ runtime libraries, branding, target registry and notices.
Original game files, saves, preferences, profiles and generated source are excluded.
The installer itself uses the static C++ runtime and Windows' cabinet services;
no additional installer builder is needed. Cabinet payloads are reused only
when their complete file manifest and archive checksum still match.

The themed per-user installer verifies a supported US Xbox XISO, optionally
copies it into the installation folder, prepares the executable/preferences,
and creates Start-menu and optional desktop shortcuts. Its worker reports real
stage/byte progress while the window remains responsive. Upgrades preserve
preferences and saves. Uninstall removes recorded application files and copied
game files while keeping saved games, preferences and the original source ISO.
Native --preview/--preview-progress BMP captures and --silent-install with
--no-register support isolated validation without operating the desktop.

Run from the source folder:

  .\tools\Build.ps1 -AllowPartial

For ongoing call recovery after preparation:

  .\tools\Build.ps1 -Stage Analysis -AllowPartial
  .\tools\Build.ps1 -Stage Game -AllowPartial

Analysis rebuilds only the small generator, checks the saved inputs, and emits
native source plus build/logs/call-recovery.json. The index lists every unique
unresolved site once, ranks shared calling patterns, and supplies original
instructions, nearby code, constructors, slot writes and direct callers. Nearby
address uses are research candidates, not proofs of writes or object types.
Caller lists cover the whole known call graph, including resolved target sets.
build/logs/call-recovery-progress.json records closed and introduced sites for
each analysis pass. A slot origin is reported
only when every recovered owner agrees; method offsets alone do not prove type.
Work through related slot/interface families in this loop before linking.
Grouped slot bindings verify each site's original pointer source automatically.

Game then builds only the game, reusing prepared media, analysis and shaders.
The default All stage performs the full workflow and refreshes both executables
and platform diagnostics. Use it for runtime changes and milestone validation;
individual call metadata changes do not require repeated platform checks.

Use -Disc 'D:\path\game.xiso.iso' to select a different image location.
The script verifies/extracts the whole disc, reuses indexed Ghidra analysis,
generates 512 native C++ shards, compiles shaders offline, builds the game and
its diagnostic tool, and checks isolated original CPU routines. Compiler work
uses one worker by default, including ThinLTO linking. Ghidra has a 3 GiB
heap and two analysis threads.
Windows builds use clang-cl, LLD and Ninja Multi-Config, with a shared CPU
precompiled header and cached ThinLTO. The script loads the x64 SDK environment
and refreshes incompatible compiler metadata while retaining extracted files,
analysis and generated sources. Both executables share a 1 GiB link cache.
Generated game code uses 512 source partitions, matching the Burnout workflow.
The changing function registry and runtime dispatcher are native objects, so
their changes cannot be imported into every game shard. Game functions retain
ThinLTO.
For direct CMake commands, first run . .\tools\Initialize-Toolchain.ps1 in the
current PowerShell session, then use cmake --preset tools or --preset windows.
After regenerating a runtime batch, cmake --build --preset release --target smbd
builds just the game for the next automated check. Refresh both executables with
the full release preset when validating a milestone.

Tools and dependencies are pinned. Unchanged analysis, generated sources and
shader banks are reused after checking their inputs. Original media, extracted
files, generated output and local storage remain ignored by Git.

-AllowPartial permits research output with unresolved control flow. Missing
functions and services stop explicitly at their original addresses. There is no
runtime CPU decoder or interpreter. The strict build rejects incomplete batches.
The initial coverage report is historical; knowledge/runtime_progress.json
records later milestones and the private reports contain current details.

Developer commands:

  .\build\windows\Release\smbd-tool.exe --help
  .\build\windows\Release\smbd-tool.exe check-image data/local/default.xbe
  .\build\windows\Release\smbd-tool.exe check-cpu data/local/default.xbe
  .\build\windows\Release\smbd-tool.exe check-image-copy
  .\build\windows\Release\smbd-tool.exe check-image-copy --warp
  .\build\windows\Release\smbd-tool.exe boot data/local/default.xbe 'Super Monkey Ball Deluxe/Super Monkey Ball Deluxe (USA).xiso.iso' 1000000 build/logs/boot.json build/logs/frame.png
  .\tools\Analyze.ps1

Boot diagnostics return 3 for unexpected boundaries and save the failure,
original register/stack history, services, file activity and graphics counters.
Reaching a requested execution budget is an expected diagnostic stop; it does
not establish playable gameplay. A frame is saved only if requested and a native
graphics device has been created.

The native game executable is build/windows/Release/smbd.exe. Run it from the
source folder. --frames COUNT, --seconds COUNT, --capture FRAME.png and --hidden
support bounded game automation. --input TIMELINE.txt connects an SDL virtual
controller. Hidden runs, input-script runs and tool boot diagnostics mute the
output stream while continuing normal mixing and playback timing. --mute also
mutes an ordinary game run. Each line is FRAME BUTTON [LEFT_X LEFT_Y], with
increasing frames;
buttons are a, b, x, y, start, back, up, down, left, right or none. A state lasts
until the next line. Stick values are -1..1, with positive Y pointing up.
For example, "120 start" followed by "122 none" presses Start for two frames.
wait32 HEX_ADDRESS HEX_MASK HEX_VALUE [BUTTON] waits for an original game state;
the optional button pulses until it matches. Following frame numbers are relative
to that match. --stop-after-input stops when all steps finish and returns 3 if a
limit or boundary interrupts the script. The short JSON output reports completion
and the number of completed waits.
The first-level research route is knowledge/first_level_input.txt. For example:

  .\build\windows\Release\smbd.exe --hidden --mute --input knowledge/first_level_input.txt --stop-after-input --seconds 60 --frames 6000 --capture build/logs/first-level.png --report build/logs/first-level.json

Automation enables SDL background controller input so hidden windows receive
these events. --report OUTPUT.json saves the shared boot report, including the
original stack, registers, file activity and service/graphics counters.
--trace-calls OUTPUT.json records unresolved native function dispatches, bounded
to 4096 site/target pairs with initial registers, stack and ordinary RAM samples.
For example, add --trace-calls build/logs/calls.json to the game command, then run:

  .\tools\Index-Calls.ps1 -Trace build/logs/calls.json

This joins observations to the complete unresolved queue and groups candidate
interfaces and shared targets across all sites. Traces identify useful static
research; observed targets never establish an exhaustive dispatch set.
check-image-copy verifies native rectangular copies, overlap, shared color images,
growth, RGB565, bounds and D3D11 validation on hardware or WARP.
The frontend provides persistent game-file, display, refresh-rate and audio
settings. Broader gameplay coverage and compatibility remain in progress.

Private outputs:

  data/local/                 Extracted media, disc inventory and executable
  data/local/analysis/        Ghidra indexes and native-generation seeds
  data/user/                  Native title storage and utility cache
  build/ghidra/               Saved Ghidra project
  build/generated/            CPU/shader sources and coverage report
  build/logs/                 Analysis, build and execution diagnostics

On Windows, the native Xbox services, D3D11 and
SDL3 input/audio are being brought up against the original program. The SEGA
startup screen and full-color title artwork render, and automated Start input
advances beyond the prompt. The Mode Select menu renders with its 3D background,
including native framebuffer-to-texture copies. CPU, controller, mixer and D3D11
diagnostics pass; knowledge/runtime_progress.json records the current counts.
Story Mode's first level, 1-1 SIMPLE, loads and responds to controller input;
the automated forward-input run reaches GOAL while the neutral comparison stays
still. Opening movies and saved settings now work. Monkey Bowling's Night-Sky
Rocket Lane is the current repeatable performance benchmark. See PLAYTEST.txt.
Remaining calls/services, complete audio and gameplay coverage, macOS,
visual parity and sustained 360 Hz performance require further work.
See runtime_progress.json
in knowledge for the current execution boundary; initial_coverage.json is historical.

Linux x86-64 and Steam Deck

On desktop Linux, use a glibc-based distribution with Clang 19 or newer,
LLD, Ninja, Git, and a Vulkan 1.4 driver compatible with DXVK Native 3.1.1.
The following command installs the prerequisites on Ubuntu 24.04.

  sudo apt install build-essential clang-19 lld-19 ninja-build git curl pkg-config patch \
    openjdk-21-jdk libssl-dev libpng-dev libjpeg-dev libasound2-dev libpulse-dev \
    libx11-dev libxext-dev libxrandr-dev libxcursor-dev libxi-dev libxfixes-dev \
    libxss-dev libxtst-dev libwayland-dev libxkbcommon-dev libdrm-dev libgbm-dev \
    libegl1-mesa-dev libgl-dev libdecor-0-dev libudev-dev libvulkan-dev \
    glslang-tools spirv-headers flex bison libjson-perl

Ensure clang, clang++ and ld.lld select the installed LLVM toolchain on PATH.
If CMake 4.2 or newer is unavailable, setup fetches the verified CMake 4.4.5
archive into build/deps. The build uses one compiler job.

  bash Install.sh '/path/to/Super Monkey Ball Deluxe (USA).xiso.iso'
  bash Play.sh

On Steam Deck, place the source in a permanent folder in your home directory or
on a Linux-formatted microSD card. Run the same setup command from Desktop Mode.
SteamOS selects the Steam Deck build automatically. On other x86-64 Linux
handhelds, pass --steamdeck to Install.sh to use that build.

Steam Deck setup installs the Freedesktop 26.08 runtime and SDK, LLVM 22 and
OpenJDK 21 through Flatpak --user. It leaves the SteamOS system partition
read-only. Allow space for the SDK, extracted assets and native build. Add the
Super Monkey Ball Deluxe application menu entry to Steam as a non-Steam game.
Leave the compatibility-tool override disabled. DXVK Native uses Vulkan
directly, and SDL3 handles Steam Input, display and audio.
The launcher retains Steam's XWayland display and allows abstract X11 sockets,
as required by Gaming Mode on some handhelds. The DXVK build includes upstream
swapchain resize fix 3dbf33cb for sharp presentation after Wayland resizes.

Desktop Linux keeps the game, settings, saves and logs under build/linux/Release.
The Deck setup uses build/steamdeck/Release and launches through the Flatpak
runtime. Rerunning Install.sh refreshes the disc path and keeps existing settings
and saves. Keep the disc image available. Launch a specific build with
bash Play.sh --linux or bash Play.sh --steamdeck.
Use a Linux filesystem for the installation and saves. When testing in WSL,
put diagnostic output and the game's --storage path on the Linux filesystem.

For terminal builds without a desktop entry, use bash Build.sh DISC or
bash Build.sh --steamdeck DISC after running bash cmake/steamdeck.sh prepare. Use
bash Build.sh --tools-only for the Linux extraction and recompilation tool.
The native builder verifies the disc, extracts the executable and shader
assets, reuses verified analysis when available, and compiles CPU helpers and
shaders ahead of time. The game reads other assets from the disc. Logs are in
the selected build directory's logs folder. WARP, the D3D11 debug layer and hardware memory
watches are Windows-only. For automated runs use --mute with the game.
The settings file picker uses SDL's native dialog. Install your desktop's XDG
portal on Wayland if the file picker is unavailable.

Ubuntu 24.04 under WSL2 passed the CPU, service, input, audio, offscreen
rendering and live presentation diagnostics with llvmpipe. The Flatpak
launcher rendered all seven settings pages over an abstract X11 socket.
The first-level replay timed out at an input wait. Physical Steam Deck
Gaming Mode, visual parity and hardware performance still need verification.
Discord Rich Presence

Settings > General > Discord Rich Presence is off by default. It shares the
game or settings state and elapsed time with Discord desktop over local IPC.
Turning it off or closing the game clears the activity. Automated and hidden
runs skip Discord. Start Discord before launching the game on Steam Deck so
Flatpak can expose its socket.

The build uses the project's Discord Application ID. Developers can override
it with -DSMBD_DISCORD_APPLICATION_ID=ID when configuring CMake. Find it under
General Information at https://discord.com/developers/applications.
